# Resumable native artifact uploads

`devbox_artifact_upload` is a C++23 host-mode tool backed by the indexed SQLite state service. It requires `MCP_STATE_BACKEND=sqlite`; existing installations must complete the guarded state migration first. `devbox_capabilities.artifact_uploads` reports availability and limits. Legacy atomic-write and large-file tools retain their contracts.

1. Call `begin` with a stable lowercase `upload_id`, a destination in the configured workspace, `total_bytes`, the whole-file `sha256`, and `expected_file_sha256` (the current file digest or `missing`). The parent directory must exist. Begin reserves capacity and leaves the destination untouched.
2. Call `chunk` with the same ID, the next `offset_bytes`, canonical `content_base64`, and that chunk's `sha256`. Chunks are sequential and at most 1 MiB. Exact retries return the durable receipt; changed bytes at an admitted offset are rejected. `status` returns the next committed offset after reconnecting.
3. Call `finalize`. Native code reads each chunk into a 64 KiB buffer, checks each chunk hash and one whole-file hash while assembling a private stage on the destination volume, checks the destination version under the existing atomic-write lock, and performs one atomic replacement.
4. Retry an uncertain finalization with the same ID. A saved completed receipt never republishes over a later edit. An interrupted finalization can reconcile by observing the expected content at the destination; that receipt explicitly identifies digest-based reconciliation rather than claiming proof of a particular earlier write.

The default limits are 1 GiB per file, 4,096 chunks, 16 active uploads, and 2 GiB of admitted payload reservations. Staged assembly can temporarily occupy another copy of an admitted payload, so the payload-storage envelope is up to 4 GiB, plus metadata and filesystem overhead. The service retains reservations until owned staging cleanup succeeds. Cancel a receiving upload to remove its staging and release its reservation. An uncertain publication is retained for reconciliation. There is no automatic expiration that silently discards acknowledged chunks.

The metadata database stores upload definitions, offsets, hashes and receipts. Payloads remain in private files. Each new chunk writes one bounded file; it does not read or copy preceding chunks. Final assembly is one additional sequential read/write of the uploaded payload. These are algorithmic I/O properties; no throughput improvement is claimed from the local fixtures. Destination CAS protects cooperating Devbox writers and detects changes observed before replacement; it does not make arbitrary external writers transactional.

Directory listing independently caps enumeration at 16,384 entries and charges buffered path/text allocations against a 4 MiB budget, even if the displayed entry limit is larger. When a bound is reached, the result explicitly says that it is partial and that only the observed subset was sorted. This buffer budget is not a whole-process RSS claim. Existing small-directory ordering is preserved.

Local verification includes native process crashes after chunk durability, before publication and after publication; resumption and cancellation of an unacknowledged chunk; simultaneous duplicate chunks; destination CAS conflict; whole/chunk hash mismatch; hardlink refusal; cross-principal lookup denial; quota retention/release; and an 8 MiB, 32-chunk fixture with unchanged prior-chunk timestamps and no cumulative prefix files. The MCP SDK exercises the new action through the real SQLite-backed server and verifies explicit refusal on the legacy backend. Hosted qualification and production promotion are tracked separately in the audit backlog.
